# 萌宠 IP 生产 Harness

> 这份文档是从「喵藏」这一天的实际过程里**反向抽出来的**。
> 不是设计稿 —— 里面每个节点都真的跑过，跑的时间和顺序都能在
> `.workbuddy/memory/2026-09-11.md`（4000 行工作日志）里对得上。
>
> 写它的目的：**下一个 IP 不用再从零摸一遍**。
>
> ⚠️ 写在 2026-09-12 上午。写的时候发现：那套一直放在 `/tmp` 的验证脚手架，
> 全盘搜不到任何痕迹了 —— 所以第六节里「收进项目」那几条是**现在最急的事**。

---

## 一、结论先行

三句话：

1. **AI 能吃掉 8 个阶段里的绝大部分** —— 代码、渲染、测试、打包、文档、自查，全都能自己闭环。
2. **人只需要在 5 个地方出现** —— 其中 3 个只是「看一眼图，选一个」，一次几秒钟。
3. **要批量生产，缺的不是能力，是抽参数** —— 7 个形象维度现在还硬编码在 `main.swift` 里，
   得先变成一份 `ip-spec.json`。

## 三、节点清单（全部 34 个）

### 阶段 0 · 立项

| 节点 | 谁 | 输入 | 产出 | 现状位置 |

| 概念澄清 | AI | 一句模糊需求 | 2~3 个可选方向 | 对话里的 AskUserQuestion |

## 四、人机接口：只有 5 个卡点

这是整个 Harness 最值得盯的地方 —— **人的每一次出现，都是对 AI 能力的定价**。

| # | 卡点 | AI 交什么给你 | 你回什么 | 单次耗时 | 频次 |
|---|---|---|---|---|---|
| 1 | 素材来源 | —（AI 查不出图从哪来） | 来源类型 | 10 秒 | 每 IP 1 次 |
| 2 | **审美拍板** | **一张并排对照图** | **「第 3 个」** | **3~10 秒** | **每 IP 40+ 次** |
| 3 | 真机试用 | 能跑的 app | 「这里不对」 | 几分钟 | 每 IP 5~10 次 |
| 4 | 合规确认 | 相似度 + 对照图 | 「可以」/「改」 | 1 分钟 | 每 IP 1~2 次 |
| 5 | 发布 | 全套物料 | 按发布键 | 几分钟 | 每 IP 1 次 |

**卡点 2 是关键**：它占了人机交互次数的 90%，但每次只要几秒。
因为它被设计成了「看图选一个」——不是「描述需求 → AI 实现 → 不满意 → 重来」。

这个设计有个前提：**AI 必须能把审美判断渲染成图**。做不到这一点，
卡点 2 就会退化成「说不清 → 改 → 还是不对 → 再改」的消耗战。

## 五、为什么这套能跑起来：ETCLOVG 视角

按你熟的那七层拆一下，看看这个 Harness 的"厚度"分布：

| 层 | 在这个项目里是什么 | 厚度 |
|---|---|---|
| **E** 执行环境 | 项目目录 + swiftc / python 工具链 + `.snapshots/` 可回滚 | 中 |
| **T** 工具接口 | 渲染脚手架、断言脚本、`fetcher.py` 的 CLI 化 | 厚 |
| **C** 上下文与记忆 | `SKILL.md`（3900 行）+ 4000 行工作日志 + 快照 | **极厚** |
| **L** 生命周期 | 8 阶段流水线 + 核心循环 + 快照机制 | 中 |
| **O** 可观测 | 离屏渲染出图、窗口实拍、指纹、诊断命令 | 厚 |
| **V** 验证与评估 | **192 条断言 + 渲染指纹 + 像素级断言** | **极厚** |
| **G** 治理 | 个人信息扫描、侵权自查、依赖许可、不写用户数据 | 中 |

**两条最值得复制的经验：**

**① V 层厚 = 敢高频改。**
一天改了 40 多次绘制代码，没有一次改崩 —— 因为每次改完立刻有
~190 条断言 + 一个渲染指纹告诉你"有没有伤到别的地方"。
对比典型的 vibe coding：改一次看一眼，改崩了不知道，等发现时已经找不回是哪一步坏的。

**② C 层厚 = 不用重新学。**
`SKILL.md` 里有 30 多条踩坑记录（`$VAR` 后接中文会炸、
`pipefail` 让 `ls | head` 变成致命错误、非活动窗口第一次点击被吃掉…）。
每一条都是花过时间才换来的。**这些是资产，不是笔记。**

## 六、批量生产：要改什么

### 现状的瓶颈

7 个形象维度（配色 / 眼型 / 瞳色 / 肚兜 / 耳朵 / 尾巴 / 嘴形）现在是
**硬编码在 `main.swift` 里的 7 个 Swift 枚举** + 一套贝塞尔绘制代码。

换一个 IP = 改代码 = 又一次完整的「阶段 1」。

### 目标形态

把槽位抽成数据，让"换 IP"变成"换一份 JSON"：

```
ip-spec.json          形象参数（每个 IP 一份）
├── palette[]         配色（刷色 + 描边 + 五官色）
├── eye[]             眼型（贝塞尔控制点）
├── eyeColor[]        瞳色
├── bib[] / ear[] / tail[] / mouth[]    配件形状
└── geometry          头部/身体比例

brand.json            文本与品牌（每个 IP 一份）
├── name / nameEn     名字
├── iconSource        图标源图路径
├── strings           界面文案
└── categories        分类词表 + fallback
```

模板见 `harness/ip-spec.example.json`。

### 改造清单（按性价比排序）

| # | 做什么 | 收益 | 成本 |
|---|---|---|---|
| 1 | **抽 `ip-spec.json`**（把 7 个枚举导成数据，绘制代码读数据） | 换 IP 从"改代码"变成"填 JSON" | 中 |
| 2 | `brand.json` 参数化（名字/文案/词表） | 一次替换，全项目生效 | 小 |
| 3 | **把验证脚手架收进 `harness/tools`** | 换个 IP 也有现成的验证管线 | 小 |
| 3b | 重建渲染套件 + 断言套件（原在 `/tmp`，已被清） | 阶段 1 全靠它 | 中 |
| 4 | 出一份"新 IP 脚手架脚本"（复制骨架 + 填槽位） | 一条命令起一个新 IP | 小 |
| 5 | 图标改成自绘矢量（现在是 254×268 位图放大） | 任何尺寸都锐利 + 无来源风险 | 小 |

第 1 项是真正的门槛，其余都是收尾。

### ⚠️ 第 3 项已经不是「建议」了 —— 它已经发生过

那套验证脚手架（渲染脚本、指纹脚本、190+ 条断言、head 副本切分工具）
**一直是放在 `/tmp/cat_export/` 的，从来没进过项目目录**。
2026-09-12 上午要拿它出来用的时候，全盘搜不到任何痕迹了。

机器当天早上 08:59 重启过，而 `/tmp` 本来就会被系统定期清理 ——
**到底是哪一下弄没的，已经查不清了，也不必查。**

因为根本原因是确定的、且跟「是谁删的」无关：**它不在项目里，所以任何一次
清理、任何一次误操作，它都没有副本。** 相比之下项目本体（`main.swift`、
77 个源码快照、内嵌引擎、DMG）因为放在 `~/Documents/ai/MiaoZaiWiki`，一样没少。

丢掉的不是几个脚本，是**这个 Harness 的 V 层** ——
没有它，下一个 IP 的每一次形象改动都只能靠肉眼，退回到 vibe coding。

**规矩定下来：任何跑得通的东西，当场落进项目目录。**
临时目录只允许放「这一分钟用完就扔」的中间文件。

## 八、下一个 IP 的操作路径

```
① 立项      ── 你给一句方向 + 形象来源
                AI 出候选名 + 商标初查 → 你定名
② 抄骨架    ── 复制生产骨架，填 ip-spec.json / brand.json
                （改造前：手改 7 个枚举 —— 见第六节第 1 项）
③ 形象      ── AI 渲染全档位对照图 → 你看图选（40+ 轮）
④ 引擎      ── AI 换分类词表，其余不动
⑤ 合规      ── AI 扫一遍 + 出对照图 → 你确认来源
⑥ 打包      ── AI 一条命令出 DMG
⑦ 分发      ── AI 出文案配图 → 你发布
```

预计：**第一个 IP 需要一天（因为要边做边搭骨架）；
有了骨架之后，第二个 IP 主要是阶段 1 的审美轮次 + 阶段 7 的物料，其余全是跑脚本。**

---

## 九、一句话总结

> 这套 Harness 的价值不在于"AI 会写代码"，
> 而在于**把「人的判断」压缩成了「看图选一个」，把「AI 的不确定性」用验证层兜住了**。
>
> 这两件事做成了，生产速度就不取决于模型多强，而取决于你能看多快。
