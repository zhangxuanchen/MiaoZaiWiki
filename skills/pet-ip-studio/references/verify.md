# 验证手册 · 怎么看它红，红了怎么办

> 一句话原则：**一条断言只在「它真的会红」的时候才算数。**
> 没验过会红的断言，等于没有。

---

## 一、跑什么

```bash
./harness/build/fingerprint --baseline    # 一行回答「默认档有没有被动过」
./harness/build/verify                    # 19 条断言，覆盖 62 个档位
```

退出码：`0` = 全过，非 0 = 有失败。所以能直接接进任何流程。

---

## 二、指纹在回答什么

```
✓ 指纹与基线一致  29B2960CAB55A8D9
```

- **一致** → 默认档**逐位相同**。你这次改动是纯新增，没碰到老路径。
- **变了** → 默认档被改了。先问自己"这是我想要的吗"：
  - 是 → 重建基线（见第五节）
  - 不是 → 你碰到了不该碰的地方，去查

**为什么这句话值钱**：人怕的从来不是"新功能坏了"（看得见），
而是"新功能把旧功能悄悄碰坏了"（看不见）。指纹把"看不见"压成一行哈希。

### 分层看：三种问题，三种工具

| 层 | 工具 | 回答 |
|---|---|---|
| 全图指纹 | `fingerprint` | **有没有变？**（最严格，逐位） |
| 差异范围 | 自己写像素比对 | **变的是不是只在该变的地方？** |
| 语义断言 | `verify` | **变得对不对？** |

顺序有讲究：第一层最便宜也最严格，它不过就不用往下看。

## 三、`verify` 的四类检查

| 检查 | 抓什么 |
|---|---|
| 默认档指纹 | 老路径被碰坏 |
| 每档可区分 | 加了新档位但渲染上和旧的一模一样（等于没加） |
| 每档非空白 | 绘制出错导致某档是空白 / 被裁 |
| 维度互不干扰 | 改 A 维度时连带改了 B |

### 输出长这样

```
✓ 默认档指纹与基线一致  29B2960CAB55A8D9
✓ 形象 4 档可区分
✓ 形象 每档都画出了东西
      · 已知重复（设计如此）：橄榄 / 跟形象
✓ 瞳色 18 档可区分
...
全部 PASS（19 条）· 覆盖 62 个档位
```

## 四、FAIL 了怎么办

### 情况 A：报「意外的重复（不在已知清单里）」

说明有两档渲染出来一模一样。**先分辨是哪一类**：

| 可能 | 判断 | 处理 |
|---|---|---|
| 设计如此 | 比如「跟形象」在奶白下正好等于「橄榄」 | 加进 `KNOWN_SAME` 白名单，**并写明原因** |
| 新档位没生效 | 加了 case 但绘制分支漏了 | 去补绘制 |
| 相位没采到 | 动效类改动在该相位下还没显现 | 换 `--phase` 再试 |

**当前已知的两组**（都在 `verify.swift` 的 `KNOWN_SAME`）：

- 瞳色：`跟形象 / 橄榄` —— 奶白形象的默认眼色本来就是橄榄绿。换个形象它们就不同了
- 表情：`待机 / 被撸` —— 「被撸」是**行为状态**，不改脸，只触发飘心耳抖。
  已在 0 / 0.2 / 0.5 / 0.8 四个相位下验证与待机逐位相同，排除相位因素

> ⚠️ **往白名单里加东西之前先确认原因。** 把 bug 塞进白名单，等于把警报器关掉。

### 情况 B：报「默认档指纹与基线不一致」

先 `git diff`（或看快照）确认你改了什么。如果确实没打算改默认档的外观，
那就是碰坏了 —— 常见原因是"新档位插在了默认档前面"，
导致下标的含义变了。

### 情况 C：某档位是空白

绘制分支里该档位没画东西，或者画到画布外被裁了。

## 五、重建基线

**只在"默认档的变化是你想要的"时才做**：

```bash
./harness/build/fingerprint > harness/baseline.txt
```

⚠️ 但 `baseline.txt` 里有一大段说明注释，直接重定向会**冲掉注释**。
正确做法是只改最后一行那个哈希值。

## 六、加一条新断言

顺序很重要：

1. **先写断言，别急着让它通过**
2. **故意把对应的地方改坏**（改一个数字就够）
3. **确认它报 FAIL**
4. 改回来，确认它报 PASS

第 2、3 步是必须的 —— 没做过这两步的断言是"装饰品"。

### 已经踩过的三种「假验证」

| 症状 | 原因 | 教训 |
|---|---|---|
| 断言"过"了，其实什么都没验 | 被测函数有缓存，第二次调用直接 return，断言里的清理逻辑没执行 | 用**没缓存过**的输入 |
| 测试看着在跑，其实跑的是旧代码 | 改了源码忘了重新编译 / 切分工具没重跑 | **编译失败必须当场停**，别拿旧二进制继续 |
| 工具说"已导出"，文件却不存在 | `try?` 把写入失败吞了 | 写文件别用 `try?` |

这三种的共同点：**都不报错，只是给你虚假的安心**。

## 七、工具链自身的结构

```
main.swift                真实源码（唯一真相）
   ↓ python3 harness/tools/mkhead.py
build/head.swift          切掉入口段后的"纯定义"
   ↓ + common.swift + <工具>.swift
build/{fingerprint,render_sheet,verify,export_spec}
```

**为什么需要 mkhead**：`main.swift` 是个完整 app（末尾 `app.run()`），
没法被测试脚本引用。切掉入口段之后，测试就能用**真实的**枚举和绘制函数 ——
不是抄一份（抄的会过时），也不是模拟的。

`mkhead.py` 会做编译检查（`swiftc -typecheck`），切歪了当场就炸。

`build.sh` 一次编译全部工具，**任一失败就退出** —— 防止"编译失败但跑旧二进制"。
